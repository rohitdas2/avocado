# Avocado mobile

React Native / Expo app for iOS and Android. Food and Lifts use the shared Flask API in `../web`, served by Gunicorn.

The app opens a guest diary automatically. Settings supports optional email accounts, name and password changes, and System, Light, or Dark appearance. Active and guest session tokens are stored with Expo SecureStore; appearance is stored locally with AsyncStorage. Creating an account keeps the current guest diary. Signing into an existing account switches diaries, and signing out restores the device's guest diary.

To use a phone during development, run the API on an address reachable from the phone and start Expo with `EXPO_PUBLIC_API_URL=http://YOUR_COMPUTER_LAN_IP:3001 npm start`. Keep the phone and computer on the same network and open the project in a compatible Expo Go version. `localhost` on a physical phone points to the phone. Restart Expo after changing the API URL.

For cross-device sync, use the same account and `EXPO_PUBLIC_API_URL` pointing to the same deployed HTTPS API and database. Guest diaries stay separate. Food and Lifts refresh when the app returns to the foreground and every 15 seconds while active, preserving form drafts. This requires a connection; offline edits and conflict resolution are not implemented.

An install outside Expo Go requires an EAS development or distribution build, configured bundle identifiers, and the relevant Apple or Android signing setup. No signed phone build is generated by the JavaScript export command.

See the root README for setup, simulator/phone connection instructions, and release limitations.

## Workouts

Lifts shows named workouts in the selected day's timeline, with local HH:mm times. Start a workout before adding exercises; starting another makes the previous one historical, including when the new workout is on a different date. Only the account's current workout has an inline exercise form. Tap its timeline row to focus that form. Tap an older workout to open a read-only summary popup; loading, refreshing, and creating workouts never open a summary automatically.

The shared backend stores `accounts → workouts → workout_exercises`. Workouts own the name/date/current status; exercises reference their workout and inherit ownership and date. Mobile uses `GET/POST /api/workouts` and `POST/DELETE /api/workouts/{id}/exercises[/exercise_id]`. No new dependencies or client storage layer were added. Workouts are available to isolated guests and remain theirs after signup.

Run `npm run db:migrate` from `../web` before using this version against your database, then restart Gunicorn. The migration preserves old lifts as one historical workout per owner/day named “Workout”; it cannot infer separate sessions from older records. New API-created workouts always have an owner; unowned legacy records stay hidden. The web interface is deferred and its existing flat lift endpoints remain compatible. See decision 28 in `../docs/architecture-decisions.md` for tradeoffs.
